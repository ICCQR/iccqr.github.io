# ICCQR architecture

ICCQR turns a display's ICC profile into a printed QR code (a *calibration marker*) that lives on the display itself. Scanning the marker opens `https://iccqr.github.io/` with the calibration encoded in the link, and the page rebuilds a working `.icc` file from it.

The whole tool is one static page. There is no server-side code and nothing is uploaded: the profile is read in the browser, and the calibration data sits after the `#` in the link, which browsers never send to the server.

```
 .icc file ──parse──▶ profile ──compact──▶ marker record ──pack──▶ bytes ──deflate──▶ base32
                                                                                       │
     printed marker (SVG) ◀── QR code ◀── https://iccqr.github.io/#<base32> ◀──────────┘

 scan ──▶ page opens with #<base32> ──▶ base32 ─▶ inflate ─▶ unpack ─▶ buildICC ─▶ Save .icc
```

## Build

`scripts/build.js` reads `src/page.html` and fills in its placeholders:

1. **Fonts.** The `<style>` block goes through the [Invisible Ink](https://github.com/Y2Z/invisible-ink) PostCSS plugin. Each `@font-face` marked `invisible-ink: hollow` gets a companion `"<Family> Placeholder"` face with an invisible, metric-identical copy of the font inlined as a data URL, and the plugin adds that family after the real one in every `font-family` and `--font-*` custom property. Text is laid out with the real font's metrics from the first frame, so nothing moves when the real font arrives. The stylesheet is processed as if it were at the repo root, so `url("fonts/…")` points at `./fonts`, the same files the site serves.
2. **Icons.** `/*ICON:<file>*/` markers become the base64 contents of `src/icons/<file>`.
3. **Scripts.** `/*QRLIB*/` becomes qrcode-generator, minified with terser. `/*CORE*/` becomes `src/core.js`. `/*APP*/` becomes `src/app.js`, with `__GLYPHS__` replaced by `src/glyphs.json`.

All dependency versions are pinned exactly in `package.json` and `package-lock.json`. With them, the build reproduces the published `index.html` byte for byte.

## The marker payload (format v1)

`src/core.js` defines the format; its header comment is the short version of this section. **This format is permanent.** Every marker ever printed carries it, so a decoder must keep reading v1 forever.

### Encoding chain

1. `compact()` reduces a parsed profile to a *marker record*.
2. `pack()` writes the record as bytes (big-endian), described below.
3. The bytes are compressed with raw DEFLATE (`CompressionStream('deflate-raw')`).
4. The result is written as base32 (RFC 4648 alphabet `A–Z 2–7`, no padding).
5. The link is `<decoder address>#<base32>`.

Base32 is chosen because its alphabet is a subset of the QR *alphanumeric* mode, which stores 5.5 bits per character instead of byte mode's 8. The QR code is therefore made of two segments: the address plus `#` in byte mode, and the payload in alphanumeric mode. A typical calibrated profile (separate R, G, B tone curves and video card curves) is about 280 compressed bytes, or about 460 characters.

### Record layout

| Field | Size | Notes |
|---|---|---|
| format | u8 | `1`. A future format bumps this; decoders reject numbers they don't know with a clear message. |
| flags | u8 | `1` chad present · `2` lumi present · `4` vcgt present · `8` one tone curve shared by R, G, B · `16` one vcgt curve shared · `32` vcgt is a formula. Bits 64 and 128 are reserved and must be 0. |
| ICC version | u8, u8 | Major and minor byte of the source profile. The rebuilt profile uses the same version. |
| date | 5 × u8 | Year − 2000, month, day, hour, minute. Year range is 2000–2255. |
| wtpt, rXYZ, gXYZ, bXYZ | 12 × int24 | Raw s15Fixed16 values from the profile, copied exactly. |
| chad | 9 × int24 | If flag 1. The chromatic adaptation matrix, raw s15Fixed16. |
| lumi | int24 | If flag 2. White luminance × 10, in cd/m². |
| tone curves | 1 or 3 curves | One if flag 8, otherwise R, G, B. |
| vcgt | formula or 1 or 3 curves | If flag 4. A formula is 9 × int24 (gamma, min, max for each channel, raw s15Fixed16). |
| description | string | The profile name your system shows. |
| model | string | Always empty now. Kept so the layout doesn't change. |
| note | string | Printed on the marker. The page limits it to 36 characters. |

A string is a u8 byte length followed by that many bytes of UTF-8 (cut at 255 bytes on a character boundary).

### Curves

Each curve starts with a kind byte:

| Kind | Body | Exact? |
|---|---|---|
| 0 identity | none | yes |
| 1 gamma | u16, u8Fixed8 gamma as in a 1-entry `curv` | yes |
| 2 parametric | u8 ICC function type (0–4), then 1, 3, 4, 5 or 7 × int24 raw s15Fixed16 parameters | yes |
| 3 sampled | u8 sample count *K*, u16 entry count of the original table, u16 gamma × 1000, then *K* zigzag varints | no, see below |

Formula curves (gamma and parametric, which DisplayCAL and ArgyllCMS often write) are copied exactly. Measured table curves (i1Profiler and many others) are resampled:

- *K* points are taken evenly across the input range (17, 33 or 65, chosen on the page; 33 by default). A table with no more than *K* entries keeps all of its entries.
- To spend precision where the eye needs it, each value *y* is stored as *t* = round(*y*^(1/γ) × 65535), where γ is the curve's own effective gamma at 50% input, clamped to 0.5–4 (γ = 1 for vcgt curves, which are close to straight lines).
- The *t* values are written as zigzag varints: *t*₀, then *t*₁ − *t*₀, then second differences. Smooth curves make these numbers tiny, which is what DEFLATE then squeezes.
- When decoding, the points are interpolated with a monotone cubic (Fritsch–Carlson), so the rebuilt curve can't overshoot or reverse.

The "Match to file" readout on the page is the largest difference between the original table and the rebuilt curve, in 8-bit code steps. It measures how faithfully the marker copies the file, not how accurate the display is. At 33 points, measured curves land well under one step.

### What a marker does not carry

LUT tags (`A2B*`, `B2A*`), measurement and metadata tags, and the profile ID. Profiles that have only LUTs are refused with an explanation. Profiles that have both a matrix/shaper and LUTs keep their matrix/shaper part, which is what most systems use for a display. A video card curve that is a straight line (an uncalibrated display) is left out.

## Rebuilding the ICC file

`buildICC()` writes a display-class (`mntr`) RGB profile with an XYZ connection space and a D50 illuminant, in the source's ICC version:

- `desc` (a v2 `desc` with an ASCII and a Unicode part, or a v4 `mluc`), and a `cprt` saying it was rebuilt from a marker.
- `wtpt`, `rXYZ`, `gXYZ`, `bXYZ`, and `chad` when present, all copied exactly.
- `rTRC`, `gTRC`, `bTRC`. When all three are identical they share one tag. Sampled curves are written back at their original table length.
- `lumi`, when present.
- `vcgt`: a formula stays a formula. Curves are written as a 3-channel, 16-bit table with at least 256 and at most 1024 entries.

Tags are 4-byte aligned and the header size matches the file length. The tests check this for every profile.

## The page

`src/app.js` shows one of two views, chosen at load:

- **Decoder**, when the link has a fragment matching `^[A-Za-z2-7]{8,}$` that decodes. It shows the date, name and note, rebuilds the profile, and offers *Save .icc file*, *Share file…* (Web Share with files, where the browser supports it) and *Copy link*. The install steps for Windows, macOS and Linux include the video card notes only when the profile has a `vcgt`.
- **Maker** otherwise. It opens with a built-in example profile (`exampleICC()`, labeled "not yours") so the page shows a real marker before a file is chosen. A chosen file never leaves the browser.

**Decoder address.** Markers link to the address the page is served from. A copy opened from disk links to `https://iccqr.github.io/`. Both can be overridden under *Encoding and link*, and the override is remembered in `localStorage` (`iccqr.base`).

**QR code.** qrcode-generator picks the smallest version that fits. Error correction is Q (25%) by default, with M and H available. If the data doesn't fit even version 40, the page explains how to make it smaller.

**Marker SVG** (`markerSVG()`), in module units, with physical size set in millimetres (0.5 mm per module by default):

- the title "ICCQR Calibration Marker", whose ink spans exactly the width of the code;
- the code with its 4-module quiet zone;
- the date, large, in IBM Plex Mono Bold;
- the note, one line.

The title and date are drawn as outlines from `src/glyphs.json`, so the marker looks the same in any browser, editor or print shop. Only the note is live text, in a monospace font stack, squeezed with `textLength` if a fallback font runs wide.

**Charts.** The gamut chart draws the CIE 1931 spectral locus (400–700 nm, 5 nm steps) as a Catmull-Rom spline closed by the line of purples, with the display's primaries and white point and sRGB for reference. Chromaticities come from the profile's primaries with D50 adaptation undone (through `chad` when present, Bradford otherwise for v2). The video card chart plots each channel's correction as output minus input, in 8-bit steps.

## Rules for changing things

- **Never change the decoder address.** It is printed on every marker. If hosting ever moves, keep `iccqr.github.io` serving a copy of the decoder, or redirect it.
- **Never change how v1 decodes.** `test/golden-v1.txt` holds a v1 payload, and the test that reads it must keep passing unchanged. A format change gets a new format number and a new decoding branch, with v1 kept as it is.
- **Keep the payload in the base32 alphabet**, so the QR code can stay in alphanumeric mode.
- **Edit `src/`, then run `npm run build`** and commit `index.html` with the source change, so the two never drift apart.
